第 07 章：Hindley-Milner 与我

第 07 章：Hindley-Milner 与我

你是什么类型？

如果你是函数式世界的新人，用不了多久，你就会发现自己已经陷在类型签名（type signature）里，深到膝盖了。类型是一门元语言，能让来自各种不同背景的人简洁高效地交流。大部分情况下，它们都是用一套叫“Hindley-Milner”的系统写成的，本章咱们就一起来研究它。

跟纯函数（pure function）打交道时，类型签名的表达力，英语在它面前连提鞋都不配。这些签名会在你耳边低语，说出一个函数最私密的秘密。只消紧凑的一行，它们就把行为和意图摊在你面前。我们还能从中推出“自由定理”（free theorem，字面意思就是“白送的定理”）。类型是可以推断出来的，所以不需要显式的类型标注。它们可以被调到纤毫毕现的精度，也可以留得笼统而抽象。它们不只对编译期检查有用，到头来还是你能拿到的最好的文档。因此，类型签名在函数式编程（functional programming）里扮演着重要的角色——比你最初以为的重要得多。

JavaScript 是门动态语言，但这不意味着我们就把类型统统抛开不管了。我们照样跟字符串、数字、布尔值等等打交道。只不过语言层面没做任何整合，所以这些信息只能装在我们自己脑子里。别担心，既然我们用签名来当文档，用注释达成目的就行。

JavaScript 也有现成的类型检查工具，比如 Flow，或者那个带类型的方言 TypeScript。本书的目标是给你配上写函数式代码的工具，所以咱们就沿用各门 FP 语言通用的那套标准类型系统。

来自地穴的晦涩传说

从数学书上积灰的书页，穿过汪洋大海般的白皮书，混在周六早上随手写的博客文章里，再一路钻进源码本身——到处都能找到 Hindley-Milner 类型签名。这套系统相当简单，但值得先花点功夫解释一下，再加上些练习，才能把这门小小的语言彻底吃透。

// capitalize :: String -> String
const capitalize = s => toUpperCase(head(s)) + toLowerCase(tail(s));

capitalize('smurf'); // 'Smurf'

这里 capitalize 接收一个 String，返回一个 String。实现先别管，我们感兴趣的是类型签名。

在 HM 里，函数写成 a -> b，其中 a 和 b 是代表任意类型的变量。所以 capitalize 的签名可以读作“从 String 到 String 的函数”。换句话说，它把一个 String 作为输入吃进去，把一个 String 作为输出吐出来。

再看几个函数签名：

// strLength :: String -> Number
const strLength = s => s.length;

// join :: String -> [String] -> String
const join = curry((what, xs) => xs.join(what));

// match :: Regex -> String -> [String]
const match = curry((reg, s) => s.match(reg));

// replace :: Regex -> String -> String -> String
const replace = curry((reg, sub, s) => s.replace(reg, sub));

strLength 跟前面是一个思路：我们拿一个 String，还你一个 Number。

其他的乍一看可能会让你犯迷糊。就算细节还没完全搞明白，你总可以把最后一个类型当成返回值。所以 match 可以理解成：它拿一个 Regex 和一个 String，还你一个 [String]。不过这里头还发生了件有意思的事，如果可以的话，我想花点时间说道说道。

对 match 而言，我们大可以把签名这样分组：

// match :: Regex -> (String -> [String])
const match = curry((reg, s) => s.match(reg));

啊对，用括号把最后一部分括起来，能透露出更多信息。现在它就被看成这样一个函数：接收一个 Regex，返回一个从 String 到 [String] 的函数。因为有柯里化（currying），事实确实如此：给它一个 Regex，我们拿回来的就是一个等着它那个 String 参数的函数。当然，我们不必非得这么想，但弄明白为什么最后一个类型才是被返回的那个，是有好处的。

// match :: Regex -> (String -> [String])
// onHoliday :: String -> [String]
const onHoliday = match(/holiday/ig);

每给一个参数，就从签名最前面弹掉一个类型。onHoliday 就是一个已经拿到 Regex 的 match。

// replace :: Regex -> (String -> (String -> String))
const replace = curry((reg, sub, s) => s.replace(reg, sub));

你看 replace 全加括号的样子——多出来的标注会显得又吵又啰嗦，所以咱们干脆把它们全省了。我们也可以选择一口气把参数全给齐，那么更省事的想法就是：replace 拿一个 Regex、一个 String、又一个 String，还你一个 String。

最后还有几件事：

// id :: a -> a
const id = x => x;

// map :: (a -> b) -> [a] -> [b]
const map = curry((f, xs) => xs.map(f));

id 函数拿任何一个老掉牙的类型 a，返回同属类型 a 的玩意儿。类型里也能用变量，就跟代码里一样。a、b 这样的变量名只是约定俗成，没什么道理可讲，你想换成什么名字都行。但只要它们是同一个变量，就必须是同一个类型。这条规则很重要，所以咱们再说一遍：a -> b 可以从任意类型 a 到任意类型 b，但 a -> a 意味着必须是同一个类型。比方说，id 可以是 String -> String，也可以是 Number -> Number，但绝不能是 String -> Bool。

map 同样用了类型变量，只不过这回我们引入了一个 b，它跟 a 可能是同一个类型，也可能不是。可以这么读：map 先拿一个从任意类型 a 到相同或不同类型 b 的函数，再拿一个由 a 组成的数组，最后得出一个由 b 组成的数组。

但愿这个类型签名里那种富于表现力的美已经把你击倒了。它几乎是一字一句地告诉我们这个函数干了什么。给它一个从 a 到 b 的函数、一个由 a 组成的数组，它就交给我们一个由 b 组成的数组。它唯一能做的正经事，就是挨个拿每个 a 去调用那个天杀的函数。干别的都是睁眼说瞎话。

能对类型以及它背后的含义进行推理，这门手艺能让你在函数式世界里走得老远。不光论文、博客、文档之类的东西变得更下饭，签名本身几乎就是在给你讲课，告诉你它有什么功能。想读得溜得靠练，但只要你咬牙坚持，大堆大堆的信息就会自动送到你面前，连 RTFM 都省了。

再来几个，看看你能不能自己把它们破译出来。

// head :: [a] -> a
const head = xs => xs[0];

// filter :: (a -> Bool) -> [a] -> [a]
const filter = curry((f, xs) => xs.filter(f));

// reduce :: ((b, a) -> b) -> b -> [a] -> b
const reduce = curry((f, x, xs) => xs.reduce(f, x));

reduce 大概是所有签名里最有表现力的一个。不过它也很刁钻，所以你要是啃不动，别觉得自己不够格。给好奇的同学：我试着用大白话解释一遍，不过你自己把签名啃下来，收获会大得多。

咳咳，那就豁出去了……看这个签名，第一个参数是一个函数，它要一个 b 和一个 a，产出一个 b。它会从哪儿弄到这些 a 和 b 呢？嗯，签名里紧接着的参数是一个 b 和一个由 a 组成的数组，所以我们只能假定那个 b 和每一个 a 都会被喂进去。我们还看到函数的结果是 b，那么这里的思路就是：我们对传进来的函数所做的最后一次念咒，就是我们的输出值。知道了 reduce 是干什么的，我们就可以说，上面这番侦查是准确的。

把可能性收窄

一旦引入类型变量，就会冒出一个古怪的性质，叫作参数性（parametricity）。这个性质说的是：一个函数会以统一的方式作用于所有类型。咱们来研究一下：

// head :: [a] -> a

看 head，我们发现它把 [a] 变成 a。除了 array 这个具体类型之外，它没有任何别的信息可用，所以它的功能就被限制在只对数组起作用。它对变量 a 一无所知，还能拿 a 干什么呢？换句话说，a 声明了自己不能是某个具体类型，也就是说它可以是任何类型，这就让我们得到一个必须对每一种想得到的类型都统一起作用的函数。参数性（parametricity）讲的就是这个。猜猜它的实现，唯一合理的假设是：它从数组里取第一个、最后一个或者随便哪个元素。head 这个名字就该给你提示了。

再来一个：

// reverse :: [a] -> [a]

光凭类型签名，reverse 到底可能在搞什么鬼？还是那句话，它没法对 a 干任何具体的事。它不能把 a 变成别的类型，不然就会冒出一个 b 来。它能排序吗？不行，它没有足够的信息去给每一种可能的类型排序。它能重新排列吗？能，我想它可以，但必须以完全可预测的同一种方式来排。还有一种可能：它决定删掉或者复制某个元素。不管怎样，重点是：它可能的行为已经被它的多态类型死死地收窄了。

可能性的收窄，还让我们能用上 Hoogle 这样的类型签名搜索引擎，去找我们想要的那个函数。塞在一个签名里的信息，威力确实相当大。

白送的定理

除了推断实现的可能性，这类推理还能白送我们一些自由定理（free theorem）。下面是从 Wadler 关于这个主题的论文里直接抄来的几个随手挑的例子。

// head :: [a] -> a
compose(f, head) === compose(head, map(f));

// filter :: (a -> Bool) -> [a] -> [a]
compose(map(f), filter(compose(p, f))) === compose(filter(p), map(f));

这些定理不用写任何代码就能拿到，它们直接由类型推出来。第一条说的是：如果我们取出数组的 head，再对它跑某个函数 f，这等价于——顺带一提，也快得多——先对每个元素 map(f)，然后取结果的 head。

你可能会想，这不就是常识嘛。可我上次查过，计算机没有常识。说真的，它们必须有套形式化的办法，才能把这类代码优化自动化。数学有本事把直觉形式化，这在计算机逻辑那片硬邦邦的地形上可太有用了。

filter 那条定理也差不多。它说的是：如果我们把 f 和 p 组合起来判断哪些该被过滤，再通过 map 真正施加 f（记住 filter 不会变换元素——它的签名强制 a 不被碰），那它总是等价于：先映射我们的 f，再用 p 这个谓词过滤结果。

这只是两个例子，但你可以把这种推理用到任何多态类型签名上，而且永远成立。在 JavaScript 里，有一些现成的工具可以声明重写规则。你也可以通过 compose 函数本身来做这件事。果子挂得低低的，可能性无穷无尽。

约束

最后还有一点要提：我们可以把类型约束到某个接口上。

// sort :: Ord a => [a] -> [a]

在这个粗箭头左边，我们看到的是对一个事实的陈述：a 必须是 Ord。换句话说，a 必须实现 Ord 接口。Ord 是什么，又是从哪儿冒出来的？在有类型的语言里，它会是一个定义好的接口，表明这些值可以排序。这不仅让我们更了解 a、更清楚 sort 函数在搞什么，也限制了它的定义域。我们把这些接口声明叫作类型约束。

// assertEqual :: (Eq a, Show a) => a -> a -> Assertion

这里我们有两个约束：Eq 和 Show。它们保证我们可以检查这些 a 是否相等，并且在它们不相等时把差异打印出来。

后面我们还会看到更多约束的例子，这个概念也会逐渐成形。

总结

Hindley-Milner 类型签名在函数式世界里无处不在。它们读起来、写起来虽然简单，但要掌握“光靠签名就理解程序”这门功夫，还得花时间。从这儿往后，我们给每一行代码都配上类型签名。
