第 13 章：幺半群把一切聚拢

第 13 章：幺半群把一切聚拢

狂野的组合

本章我们要借半群（semigroup）来考察幺半群（monoid）。幺半群是数学抽象头发里粘上的那块口香糖。它们抓住的是一个横跨多个学科的观念，无论比喻意义上还是字面意义上，都把这一切聚拢到一起。它们是把所有会计算的东西连起来的那股不祥之力。是我们代码库里的氧气，是代码跑在其上的大地，是编码出来的量子纠缠。

幺半群（semigroup）讲的是组合。可组合又是什么？它能意味着太多东西：从累加到拼接，到乘法，到选择、组合、排序，甚至求值！这里我们会看到很多例子，但我们只会在幺半群那座山的山脚下踮着脚尖走几步。实例要多少有多少，应用也广得很。本章的目标是给你一个靠谱的直觉，好让你自己能造出一些幺半群来。

把加法抽象出来

加法有些有趣的性质，我想聊聊。咱们戴上抽象护目镜来瞧瞧它。

首先，它是一个二元运算，也就是说，这个运算接收两个值、吐出一个值，而且全都在同一个集合里。

// 一个二元运算
1 + 1 = 2

看到了吧？定义域里两个值，陪域里一个值，还是同一个集合——可以说，就是数。有人会说数在加法下是“封闭的”，意思是无论把哪些数扔进这锅汤里，类型都不会变。这就意味着我们可以把运算串起来，因为结果永远是另一个数：

// 我们可以对任意多个数这么干
1 + 7 + 5 + 4 + ...

除此之外（这双关真是算计出来的……），我们还有结合律，它给我们买来了想怎么分组就怎么分组的自由。顺带一提，一个满足结合律的二元运算正是并行计算的配方，因为我们可以把活儿切块、分发出去。

// 结合律
(1 + 2) + 3 = 6
1 + (2 + 3) = 6

现在，可别把这个跟交换律搞混了——交换律允许我们重排顺序。加法确实满足交换律，可我们眼下对那条性质没那么感兴趣——对我们的抽象需求来说，它太具体了。

仔细想想，我们的抽象超类里到底该放哪些性质？哪些特征是加法独有的，哪些可以泛化？这个层级结构中间还夹着别的抽象吗，还是说就是一整块？我们的数学先辈在构想抽象代数里那些接口的时候，用的就是这种思路。

碰巧，那帮老派的抽象派在抽象加法的时候，落脚到了群这个概念上。群什么花活儿都有，连负数这个概念都包括在内。可我们这儿只对那个满足结合律的二元运算感兴趣，所以我们选个没那么具体的接口：半群（Semigroup）。半群是一种带 concat 方法的类型，这个方法就充当那个满足结合律的二元运算。

咱们给加法实现一个，就叫它 Sum：

const Sum = x => ({
  x,
  concat: other => Sum(x + other.x)
})

注意，我们是跟另一个 Sum 做 concat，返回的永远还是一个 Sum。

我在这儿用了个对象工厂，没走咱们平常那套原型仪式，主要是因为 Sum 不是指向函子（pointed），我们也不想被迫敲 new。不管怎么说，用起来是这样：

Sum(1).concat(Sum(3)) // Sum(4)
Sum(4).concat(Sum(37)) // Sum(41)

就这么一下，我们就能面向接口编程，而不是面向实现编程。因为这个接口来自群论，背后有几百年的文献给它撑腰。免费的文档啊！

现在，就像刚才说的，Sum 不是指向函子，也不是函子（functor）。作为练习，回去翻翻那些定律，看看为什么。好吧，我直接告诉你：它只能装一个数，所以 map 在这儿讲不通，因为我们没法把底下的值变换成别的类型。那样的 map 可真是极其有限！

那这有什么用？嗯，跟任何接口一样，我们可以把实例换掉，换出不同的结果：

const Product = x => ({ x, concat: other => Product(x * other.x) })

const Min = x => ({ x, concat: other => Min(x < other.x ? x : other.x) })

const Max = x => ({ x, concat: other => Max(x > other.x ? x : other.x) })

不过这可不限于数字。咱们再看几种别的类型：

const Any = x => ({ x, concat: other => Any(x || other.x) })
const All = x => ({ x, concat: other => All(x && other.x) })

Any(false).concat(Any(true)) // Any(true)
Any(false).concat(Any(false)) // Any(false)

All(false).concat(All(true)) // All(false)
All(true).concat(All(true)) // All(true)

[1,2].concat([3,4]) // [1,2,3,4]

"miracle grow".concat("n") // miracle grown"

Map({day: 'night'}).concat(Map({white: 'nikes'})) // Map({day: 'night', white: 'nikes'})

你要是盯着这些看久了，那模式就会像立体画（magic eye poster）一样“啪”地蹦到你眼前。它无处不在。我们在合并数据结构、组合逻辑、拼字符串……看起来几乎什么任务都能被硬敲进这个基于组合的接口里。

我已经用过好几次 Map 了。要是你俩还没正式认识过，恕我失礼。Map 不过是把 Object 包了一层，这样我们就能给它添点额外的方法，还不用改动宇宙的构造。

我最爱的函子都是半群。

到目前为止我们见过的那些实现了函子接口的类型，也都实现了半群接口。来看看 Identity（就是那位从前叫 Container 的艺术家）：

Identity.prototype.concat = function(other) {
  return new Identity(this.__value.concat(other.__value))
}

Identity.of(Sum(4)).concat(Identity.of(Sum(1))) // Identity(Sum(5))
Identity.of(4).concat(Identity.of(1)) // TypeError: this.__value.concat is not a function

当且仅当它的 __value 是半群时，它才是半群。就像一个手滑得跟抹了黄油似的悬挂滑翔者：只要还抓着一个半群，它就是个半群。

其他类型的行为也差不多：

// 带上错误处理来组合
Right(Sum(2)).concat(Right(Sum(3))) // Right(Sum(5))
Right(Sum(2)).concat(Left('some error')) // Left('some error')


// 异步组合
Task.of([1,2]).concat(Task.of([3,4])) // Task([1,2,3,4])

当我们把这些半群摞成级联式的组合时，这就特别好用：

// formValues :: Selector -> IO (Map String String)
// validate :: Map String String -> Either Error (Map String String)

formValues('#signup').map(validate).concat(formValues('#terms').map(validate)) // IO(Right(Map({username: 'andre3000', accepted: true})))
formValues('#signup').map(validate).concat(formValues('#terms').map(validate)) // IO(Left('one must accept our totalitarian agreement'))

serverA.get('/friends').concat(serverB.get('/friends')) // Task([friend1, friend2])

// loadSetting :: String -> Task Error (Maybe (Map String Boolean))
loadSetting('email').concat(loadSetting('general')) // Task(Maybe(Map({backgroundColor: true, autoSave: false})))

最上面那个例子里，我们把一个装着 Either、Either 里又装着 Map 的 IO 组合起来，用来校验并合并表单的值。接着，我们访问了几台不同的服务器，用 Task 和 Array 以异步的方式把结果合并起来。最后，我们把 Task、Maybe 和 Map 摞起来，用来加载、解析并合并多项设置。

这些当然也能用 chain 或 ap 来做，但半群把我们要干的事表达得简洁多了。

这还超出了函子的范围。事实上，只要一个东西完全由半群组成，它自己就是半群：既然零碎能 concat，那一整包自然也能 concat。

const Analytics = (clicks, path, idleTime) => ({
  clicks,
  path,
  idleTime,
  concat: other =>
    Analytics(clicks.concat(other.clicks), path.concat(other.path), idleTime.concat(other.idleTime))
})

Analytics(Sum(2), ['/home', '/about'], Right(Max(2000))).concat(Analytics(Sum(1), ['/contact'], Right(Max(1000))))
// Analytics(Sum(3), ['/home', '/about', '/contact'], Right(Max(2000)))

瞧，每样东西都知道怎么把自己漂漂亮亮地组合起来。而且你猜怎么着，我们只要用 Map 类型，就能白得同样的效果：

Map({clicks: Sum(2), path: ['/home', '/about'], idleTime: Right(Max(2000))}).concat(Map({clicks: Sum(1), path: ['/contact'], idleTime: Right(Max(1000))}))
// Map({clicks: Sum(3), path: ['/home', '/about', '/contact'], idleTime: Right(Max(2000))})

想摞多少、组合多少都随你。不过就是往森林里再添一棵树，或者往森林大火里再添一把火——看你代码库是哪种情况。

默认的、直觉的行为，是组合类型里装的东西；不过有些情况下，我们会不管里面装了什么，直接组合容器本身。想想 Stream 这样的类型：

const submitStream = Stream.fromEvent('click', $('#submit'))
const enterStream = filter(x => x.key === 'Enter', Stream.fromEvent('keydown', $('#myForm')))

submitStream.concat(enterStream).map(submitForm) // Stream()

我们可以把两个事件流里的事件都逮过来，合成一条新流，从而把它们组合起来。另一种做法是坚持让它们装着半群，再按半群来组合。事实上，每个类型都可能有很多种实例。拿 Task 来说，我们可以挑两个里较早或较晚的那个来组合。我们也可以总是选第一个 Right，而不是一遇到 Left 就短路——前者相当于把错误忽略掉。有个接口叫 Alternative，它实现的正是其中一些——嗯——另类的实例，通常专注于“选择”而不是级联组合。你要是需要这类功能，值得去研究研究。

白送的幺半群

我们本来在抽象加法，可是跟巴比伦人一样，我们缺了零这个概念（关于它，一共被提到了零次）。

零扮演的是恒等的角色，意思是任何元素加上 0，都会原样返回同一个元素。从抽象的角度说，把 0 想成一种中性的、或者说空的元素，是很有帮助的。重要的是，它在我们二元运算的左边和右边得表现一致：

// 恒等
1 + 0 = 1
0 + 1 = 1

我们把这个概念叫作 empty，并为它造一个新接口。跟许许多多创业公司一样，我们挑了个恶心得毫无信息量、但方便谷歌的名字：幺半群（Monoid）。幺半群的配方是：拿任何一个半群，再加一个特殊的恒等元素。我们会用类型自身上的一个 empty 函数来实现它：

Array.empty = () => []
String.empty = () => ""
Sum.empty = () => Sum(0)
Product.empty = () => Product(1)
Min.empty = () => Min(Infinity)
Max.empty = () => Max(-Infinity)
All.empty = () => All(true)
Any.empty = () => Any(false)

一个空的、恒等的值，什么时候能派上用场？这就像在问零有什么用。等于啥也没问……

当我们一无所有的时候，能指望谁？零。我们想要多少个 bug？零个。它是我们对不安全代码的容忍度。一个全新的开始。终极价签。它能把路径上的一切都灭掉，也能在紧要关头救我们一把。是金光闪闪的救生圈，也是绝望的深渊。

在代码里，它们对应着合理的默认值：

const settings = (prefix="", overrides=[], total=0) => ...

const settings = (prefix=String.empty(), overrides=Array.empty(), total=Sum.empty()) => ...

或者在别无他物的时候，返回一个有用的值：

sum([]) // 0

它们还是累加器最完美的初始值……

把房子折塌

巧得很，concat 和 empty 恰好能塞进 reduce 的头两个位置。我们其实可以不管空值，直接对一个半群组成的数组做 reduce，可你也看到了，这会弄出一个岌岌可危的局面：

// concat :: Semigroup s => s -> s -> s
const concat = x => y => x.concat(y)

[Sum(1), Sum(2)].reduce(concat) // Sum(3)

[].reduce(concat) // TypeError: Reduce of empty array with no initial value

炸药就这么“轰”了。就像马拉松里崴了脚，我们给自己弄了个运行时异常。JavaScript 特别乐意让我们在开跑之前把枪绑在球鞋上——我猜它算是挺保守的一种语言吧——可一旦数组荒了，它就让我们原地熄火。话说回来，它能返回什么呢？NaN、false、-1？要是程序还得往下走，我们想要的是类型正确的结果。它可以返回一个 Maybe 来表示失败的可能，但我们还能做得更好。

咱们用柯里化（currying）的 reduce 函数，做一个安全版本，让 empty 值不再是可选的。从今往后，它就叫 fold：

// fold :: Monoid m => m -> [m] -> m
const fold = reduce(concat)

开头那个 m 就是我们的 empty 值——我们中性的起点；然后我们拿一个由 m 组成的数组，把它们压成一颗漂亮的、钻石般的值。

fold(Sum.empty(), [Sum(1), Sum(2)]) // Sum(3)
fold(Sum.empty(), []) // Sum(0)

fold(Any.empty(), [Any(false), Any(true)]) // Any(true)
fold(Any.empty(), []) // Any(false)


fold(Either.of(Max.empty()), [Right(Max(3)), Right(Max(21)), Right(Max(11))]) // Right(Max(21))
fold(Either.of(Max.empty()), [Right(Max(3)), Left('error retrieving value'), Right(Max(11))]) // Left('error retrieving value')

fold(IO.of([]), ['.link', 'a'].map($)) // IO([<a>, <button class="link"/>, <a>])

最后两个例子里，我们手动提供了一个 empty 值，因为没法在类型自身上定义它。这完全没问题。带类型的语言自己就能琢磨出来，可我们在这儿得手动传进去。

还算不上幺半群

有些半群没法变成幺半群，也就是说，没法提供一个初始值。看看 First：

const First = x => ({ x, concat: other => First(x) })

Map({id: First(123), isPaid: Any(true), points: Sum(13)}).concat(Map({id: First(2242), isPaid: Any(false), points: Sum(1)}))
// Map({id: First(123), isPaid: Any(true), points: Sum(14)})

我们会合并几个账号，保留 First 的那个 id。我们没法给它定义一个 empty 值。但这不代表它没用。

大统一理论

群论还是范畴论？

二元运算这个概念在抽象代数里到处都是。事实上，它就是范畴的首要运算。可是在范畴论（category theory）里，没有恒等，我们没法给自己的运算建模。这就是为什么我们从群论里的半群出发，等有了空之后，再跳到范畴论里的幺半群。

幺半群构成一个单对象范畴：态射（morphism）是 concat，恒等是 empty，而组合是有保证的。

组合即幺半群

类型为 a -> a、定义域和陪域落在同一个集合里的函数，叫作自同态（endomorphism）。我们可以造一个叫 Endo 的幺半群来抓住这个想法：

const Endo = run => ({
  run,
  concat: other =>
    Endo(compose(run, other.run))
})

Endo.empty = () => Endo(identity)


// 实际使用中

// thingDownFlipAndReverse :: Endo [String] -> [String]
const thingDownFlipAndReverse = fold(Endo(() => []), [Endo(reverse), Endo(sort), Endo(append('thing down')])

thingDownFlipAndReverse.run(['let me work it', 'is it worth it?'])
// ['thing down', 'let me work it', 'is it worth it?']

因为它们都是同一个类型，我们可以借 compose 来做 concat，类型永远对得上。

单子即幺半群

你可能已经注意到，join 是一个这样的运算：它接收两个（嵌套的）单子（monad），以符合结合律的方式把它们压成一个。它同时也是一种自然变换（natural transformation），或者说“函子函数”。前面说过，我们可以把函子当作对象、把自然变换当作态射，构成一个范畴。现在，如果我们把它特化到自函子（endofunctor），也就是同一类型的函子，那么 join 就给了我们一个自函子范畴里的幺半群，也就是单子。要把这个精确表述写成代码，还得耍点小花招——我鼓励你自己去谷歌——不过大体思路就是这样。

应用函子即幺半群

就连应用函子（applicative functor）也有幺半群式的表述，在范畴论里叫松弛幺半函子（lax monoidal functor）。我们可以把这个接口实现成幺半群，再从里头把 ap 捞回来：

// concat :: f a -> f b -> f [a, b]
// empty :: () -> f ()

// ap :: Functor f => f (a -> b) -> f a -> f b
const ap = compose(map(([f, x]) => f(x)), concat)

小结

所以你看，万物皆有关联，或者说，都可以被关联起来。这个深刻的领悟让幺半群成了一件强大的建模工具，从应用架构的大片疆土，到数据里最小的碎片，都用得上。我鼓励你，只要应用里出现了直接的累加或组合，就想想幺半群；等这个掌握牢了，再开始把定义往更多应用上抻（你会惊讶于一个幺半群能建模多少东西）。
