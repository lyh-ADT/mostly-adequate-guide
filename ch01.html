第 01 章：我们到底在干什么？

第 01 章：我们到底在干什么？

自我介绍

嗨！我是 Franklin Frisby 教授。很高兴认识你。接下来我们要相处一阵子了，因为我要教你一点函数式编程（functional programming）。不过说够我了，你呢？我希望你至少对 JavaScript 这门语言有点熟悉，有那么一丁点儿面向对象的经验，并且自认是个劳动阶级程序员。你不需要有昆虫学博士学位，你只要知道怎么找到并干掉几只 bug 就行。

我不会假设你之前学过函数式编程，因为咱俩都知道"想当然"会有什么下场（英语里那句老话说：你一 assume，就把你和我都变成了 ass，也就是蠢驴）。不过，我确实指望你遇到过一些不太美妙的状况——那种跟可变状态、不受约束的副作用（side effect）以及不讲原则的设计打交道时冒出来的状况。既然咱们已经正式认识了，那就开始吧。

本章的目的是让你感受一下：我们写函数式程序时到底图个啥。为了能看懂后面的章节，我们得先大概知道，一个程序凭什么算得上函数式。否则我们就会漫无目的地乱涂乱画，不惜一切代价躲开对象——那可真是笨手笨脚。我们需要一个清晰的靶心，好把代码往上扔；还需要一个天体罗盘，好在风浪大起来的时候指个方向。

当然，编程界有一些通用原则——各种首字母缩写的信条，指引我们穿过任何应用的黑暗隧道：DRY（别重复自己）、YAGNI（你压根儿不会用到它）、松耦合高内聚、最小惊讶原则、单一职责，等等等等。

我不会把多年来听过的每条准则都列出来烦你……关键在于，这些原则在函数式环境里同样成立，尽管它们跟我们的终极目标只是沾亲带故。现在，在继续往下走之前，我想让你先感受一下：当我们对着键盘戳戳捅捅的时候，心里到底打的什么算盘；我们的函数式世外桃源。

一次短暂的邂逅

咱们从一点疯狂开始。下面是一个海鸥应用。当两群海鸥合群时，它们会变成更大的一群；当它们繁殖时，数量会按交配对象的海鸥数量成倍增长。注意，这可不是什么好的面向对象代码，它放在这儿是为了凸显我们这种现代、基于赋值的做法有多危险。请看：

class Flock {
  constructor(n) {
    this.seagulls = n;
  }

  conjoin(other) {
    this.seagulls += other.seagulls;
    return this;
  }

  breed(other) {
    this.seagulls = this.seagulls * other.seagulls;
    return this;
  }
}

const flockA = new Flock(4);
const flockB = new Flock(2);
const flockC = new Flock(0);
const result = flockA
  .conjoin(flockC)
  .breed(flockB)
  .conjoin(flockA.breed(flockB))
  .seagulls;
// 32

到底是谁造出了这么个天杀的怪物？要跟踪这种不断变化的内部状态，简直难到不讲道理。而且，我的天，答案还是错的！本应该是 16，可 flockA 在这个过程中被永久地改掉了。可怜的 flockA。这是 IT 界的无政府状态！这是野兽派算术！

如果你没看懂这个程序，没关系，我也没看懂。这里要记住的一点是：状态和可变的值很难跟踪，哪怕例子这么小也一样。

咱们再试一次，这回用更函数式的做法：

const conjoin = (flockX, flockY) => flockX + flockY;
const breed = (flockX, flockY) => flockX * flockY;

const flockA = 4;
const flockB = 2;
const flockC = 0;
const result =
    conjoin(breed(flockB, conjoin(flockA, flockC)), breed(flockA, flockB));
// 16

这回我们得到了正确答案，而且代码少得多。函数的嵌套是有点让人晕头转向……（这个问题我们会在第 5 章解决）。好一些了，但咱们再往下挖挖。是铲子就叫铲子，这有好处的。要是当初我们把自己的自定义函数仔细端详一番，就会发现我们不过在跟简单的加法（conjoin）和乘法（breed）打交道。

这两个函数除了名字之外，真的一点都不特别。咱们把它们改名为 multiply 和 add，好揭露它们的真实身份。

const add = (x, y) => x + y;
const multiply = (x, y) => x * y;

const flockA = 4;
const flockB = 2;
const flockC = 0;
const result =
    add(multiply(flockB, add(flockA, flockC)), multiply(flockA, flockB));
// 16

就这样，我们掌握了上古先贤的知识：

// 结合律
add(add(x, y), z) === add(x, add(y, z));

// 交换律
add(x, y) === add(y, x);

// 恒等律
add(x, 0) === x;

// 分配律
multiply(x, add(y,z)) === add(multiply(x, y), multiply(x, z));

啊对，这些老掉牙却忠实的数学性质，迟早派得上用场。你要是没法脱口而出，也不用担心。我们很多人上一次学这些算术定律，已经是好久以前的事了。看看能不能用这些性质来简化我们的小海鸥程序。

// 原来的那一行
add(multiply(flockB, add(flockA, flockC)), multiply(flockA, flockB));

// 应用恒等律去掉多余的 add
// (add(flockA, flockC) == flockA)
add(multiply(flockB, flockA), multiply(flockA, flockB));

// 应用分配律得到结果
multiply(flockB, add(flockA, flockA));

漂亮！除了调用函数，我们一行自定义代码都不用写。这里给出 add 和 multiply 的定义只是为了完整性，其实压根儿不用自己写——现有的某个库里肯定早就提供了 add 和 multiply。

你可能会想："你也太会树靶子了吧，一上来就摆这么个数学例子。"或者："真实程序可没这么简单，没法这样推理。"我选这个例子，是因为我们大多数人早就懂加法和乘法，所以很容易看出数学在这里有多管用。

别灰心——整本书里，我们会撒进一点范畴论（category theory）、集合论和 lambda 演算，还会写一些真实世界的例子，让它们达到跟海鸥例子一样优雅的简洁和结果。你也不必是数学家。一切都会显得自然而轻松，就像你在用一个"正常"的框架或 API 一样。

要是听说我们能照着上面那个函数式类比，写出完整的日常应用，你可能会吃惊。程序要有健全的性质。程序要简洁，却又容易推理。程序不要在每一处都重新发明轮子。如果你是个罪犯，无法无天是好事；但在这本书里，我们想承认并遵守数学的定律。

我们会想要这样一套理论：其中的每个部件都彬彬有礼地彼此契合。我们会想用通用的、可组合的零件来表示我们的具体问题，然后为了自己的私利去利用它们的性质。这比命令式编程那种"怎么都行"的路子要多一点纪律（"命令式"的精确定义我们会在书后面讨论，现在你就把它当成函数式编程以外的任何东西好了）。在有原则的数学框架里工作，回报会让你真正大吃一惊。

我们瞥见了函数式北极星的一丝微光，但在真正启程之前，还有几个具体概念要抓住。
