第 02 章：一等函数

第 02 章：一等函数

快速回顾

当我们说函数是"一等公民"（first class）时，意思是它们跟大伙儿没什么两样……换句话说，就是个普通阶级（class）。我们可以像对待任何其他数据类型那样对待函数，它们没什么特别之处——可以存进数组，可以当参数传来传去，可以赋给变量，诸如此类。

这是 JavaScript 入门第一课，但值得一提，因为你在 GitHub 上随便搜搜代码就会发现，大家都在集体回避这个概念，或者干脆说，普遍对它一无所知。要不要来个装模作样的例子？来吧。

const hi = name => `Hi ${name}`;
const greeting = name => hi(name);

这里，greeting 里包着 hi 的那层函数包装完全多余。为什么？因为 JavaScript 里的函数是可调用的。hi 后面带上 () 时，它就会执行并返回一个值；不带 () 时，它只是把存在变量里的那个函数原样返回。不信你自己看：

hi; // name => `Hi ${name}`
hi("jonas"); // "Hi jonas"

既然 greeting 只不过是原封不动地把同一个参数转手传给 hi，那我们大可直接写成：

const greeting = hi;
greeting("times"); // "Hi times"

换句话说，hi 本身就已经是个接收一个参数的函数了，干嘛还要在外面再套一层函数，就为了用同一个见鬼的参数去调 hi？这毫无道理。就好比七月中旬你裹上最厚的派克大衣，把空调开到最大，然后要一根冰棍。

仅仅为了延迟求值就给函数套一层函数，这种写法既烦人地啰嗦，又恰好是坏实践（原因马上就会看到，跟维护性有关）。

继续往下之前，扎实地理解这一点至关重要。所以我们再从 npm 包这个"图书馆"里挖几个有趣的例子来看看。

// 蒙昧
const getServerStuff = callback => ajaxCall(json => callback(json));

// 开悟
const getServerStuff = ajaxCall;

这世上到处都散落着跟这一模一样的 ajax 代码。下面说明为什么两者等价：

// 这一行
ajaxCall(json => callback(json));

// 等同于这一行
ajaxCall(callback);

// 所以重构 getServerStuff
const getServerStuff = callback => ajaxCall(callback);

// ……等价于这个
const getServerStuff = ajaxCall; // <-- 妈你看，没有 ()

各位，事情就是这么办的。再来一遍，好让我们明白我为什么这么啰嗦。

const BlogController = {
  index(posts) { return Views.index(posts); },
  show(post) { return Views.show(post); },
  create(attrs) { return Db.create(attrs); },
  update(post, attrs) { return Db.update(post, attrs); },
  destroy(post) { return Db.destroy(post); },
};

这个荒唐的控制器有 99% 是废话。我们可以把它重写成：

const BlogController = {
  index: Views.index,
  show: Views.show,
  create: Db.create,
  update: Db.update,
  destroy: Db.destroy,
};

……或者干脆把它整个废掉，因为它唯一的作用就是把我们的 Views 和 Db 捆在一起。

为什么偏爱一等函数？

好，咱们来认真数数偏爱一等函数（first-class function）的理由。就像在 getServerStuff 和 BlogController 例子里看到的，人很容易加上一层层间接调用，既不增加价值，又只会让需要维护和搜索的冗余代码变多。

此外，如果这样一个没必要包一层的函数本身需要改动，我们还得跟着改自己的包装函数。

httpGet('/post/2', json => renderPost(json));

要是 httpGet 改成可能传一个 err 过来，我们就得回头去改这些"胶水"代码。

// 回到应用里每一个 httpGet 调用，把 err 显式地传下去。
httpGet('/post/2', (json, err) => renderPost(json, err));

要是当初就写成一等函数，需要改的地方就少得多：

// renderPost 在 httpGet 内部被调用，参数多少个都随它
httpGet('/post/2', renderPost);

除了去掉多余的函数，我们还必须给参数起名字、引参数。你看，名字这事儿有点麻烦。搞不好就会起错名字——尤其是代码库上了年纪、需求也变了的时候。

同一个概念有多个名字，是项目里常见的混乱来源。泛型代码也有类似问题。比如，下面这两个函数做的事一模一样，但其中一个让人感觉无限地更通用、更可复用：

// 只针对我们当前的博客
const validArticles = articles =>
  articles.filter(article => article !== null && article !== undefined),

// 对将来的项目而言通用得多
const compact = xs => xs.filter(x => x !== null && x !== undefined);

用了具体的命名，我们似乎就把自己跟特定的数据绑在了一起（这里就是 articles）。这种事经常发生，也是大量重复造轮的根源。

我必须提一句：就跟面向对象代码一样，你得当心 this 咬你脖子。如果底层函数用到了 this，而我们又把它当一等函数来调用，那就要承受这个泄漏抽象（leaky abstraction）的怒火。

const fs = require('fs');

// 吓人
fs.readFile('freaky_friday.txt', Db.save);

// 好些了
fs.readFile('freaky_friday.txt', Db.save.bind(Db));

把 Db 绑定到它自己之后，它就能自由访问自己原型上的那些垃圾代码了。我躲 this 就像躲脏尿布。写函数式代码时真没这个必要。不过，跟其他库打交道时，你可能不得不迁就一下我们周围这个疯狂的世界。

有人会争辩说，this 对优化速度必不可少。如果你属于那种热衷微优化的人，请合上这本书。要是钱退不了，也许你可以换一本更琐碎折腾的书。

就这样，我们可以继续了。
