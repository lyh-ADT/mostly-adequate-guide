第 10 章：应用函子

第 10 章：应用函子

把应用函子应用起来

应用函子（applicative functor）这名字，考虑到它的函数式出身，算是相当形象了。函数式程序员在起名这件事上臭名昭著，动不动就搞出 mappend 或者 liftA4 这种玩意儿——搁数学实验室里看，那叫一个浑然天成；可一出了那个门，它们的清晰度就跟得来速窗口前拿不定主意的达斯·维达差不多。

不管怎么说，这名字应该已经把底儿漏了：这个接口给我们的，是把函子（functor）互相应用起来的能力。

那么问题来了：一个像你这样正常、理性的人，为什么想要这种东西？把一个函子应用到另一个函子上，这到底是什么意思？

要回答这些问题，咱们先从你在函数式旅途上可能已经撞见过的一种情况说起。假设——纯属假设啊——我们手里有两个（同类型的）函子，想拿它们俩的值当参数去调用同一个函数。就来点简单的：把两个 Container 的值加起来。

// 这么干不行，因为数字都被装瓶子里了。
add(Container.of(2), Container.of(3));
// NaN

// 用上咱们那可靠的老伙计 map
const containerOfAdd2 = map(add, Container.of(2));
// Container(add(2))

现在我们手上有了一个 Container，里面装着一个部分应用（partial application）的函数。更准确地说，我们有一个 Container(add(2))，想把里面的 add(2) 应用到 Container(3) 里的那个 3 上，好把这次调用补全。换句话说，我们想把一个函子应用到另一个函子上。

巧的是，完成这件事的工具咱们其实早就有了。我们可以先 chain，再 map 那个部分应用的 add(2)，就像这样：

Container.of(2).chain(two => Container.of(3).map(add(two)));

问题在于，我们被困在了单子（monad）的顺序世界里：前一个单子没把手头的事办完，后面什么都别想求值。可咱们手里明明是两条好汉、两个独立的值，为了满足单子那点顺序要求，就非得把 Container(3) 的创建往后拖，我觉得这完全没必要。

事实上，要是我们不小心掉进了这个泡菜坛子，能干净利落地把一个函子的内容应用到另一个函子的值上，不写那些多余的函数和变量，那该多美。

瓶中船

ap 是个函数，能把一个函子里的函数内容应用到另一个函子的值内容上。这句话你快速念五遍试试。

Container.of(add(2)).ap(Container.of(3));
// Container(5)

// 现在，全体一起上

Container.of(2).map(add).ap(Container.of(3));
// Container(5)

这就成了，干净利落。对 Container(3) 来说是个好消息，它总算从嵌套单子函数的大牢里放出来了。值得再提一句：这里的 add 是在第一次 map 的时候被部分应用的，所以只有当 add 是柯里化（currying）的，这一套才玩得转。

ap 可以这么定义：

Container.prototype.ap = function (otherContainer) {
  return otherContainer.map(this.$value);
};

记住，this.$value 会是个函数，而我们接收的是另一个函子，所以只需要 map 一下就行。于是我们就有了接口定义：

应用函子就是一个带 ap 方法的 pointed 函子

注意这里对 pointed 的依赖。pointed 接口在这儿的地位至关重要，后面的例子会一直印证这一点。

我感觉到你在怀疑（也许还有困惑和惊恐），不过先把心敞开；ap 这家伙迟早会派上用场。在深入之前，咱们先来探索一条漂亮的性质。

F.of(x).map(f) === F.of(f).ap(F.of(x));

说人话就是：对 f 做 map，等价于把一个装着 f 的函子拿去 ap。说得再白一点：我们可以把 x 放进容器然后 map(f)，或者把 f 和 x 都提进容器然后 ap 它们。这样一来，我们就能从左往右地写代码了：

Maybe.of(add).ap(Maybe.of(2)).ap(Maybe.of(3));
// Maybe(5)

Task.of(add).ap(Task.of(2)).ap(Task.of(3));
// Task(5)

你眯着眼睛看的话，甚至能认出这隐约就是一次普通函数调用的形状。无值风格（pointfree）的写法我们本章后面再聊，眼下这就是写这类代码的首选。用 of，每个值都被运送到容器这个魔法世界——一个平行宇宙，在那里每次应用都可能是异步的、可能是 null，或者随便什么名堂，而 ap 会在这片奇幻之地里把函数应用起来。这就像在瓶子里造船。

看见没？刚才例子里我们用的是 Task。这正是应用函子大显身手的典型场面。咱们看个更深入的例子。

协调的动机

假设咱们在做一个旅游网站，想同时取回一份旅游景点列表和一份本地活动列表。这两个各自都是独立的、自成一体的 API 调用。

// Http.get :: String -> Task Error HTML

const renderPage = curry((destinations, events) => { /* 渲染页面 */ });

Task.of(renderPage).ap(Http.get('/destinations')).ap(Http.get('/events'));
// Task("<div>some page with dest and events</div>")

两个 Http 调用会立刻发生，等两边都 resolve 了，renderPage 就会被调用。对比一下单子版本：那儿必须等一个 Task 完成，下一个才能发车。既然我们取活动并不需要景点数据，那自然就不用被顺序求值捆住手脚。

还是那句话，因为我们靠部分应用来达成这个结果，所以必须保证 renderPage 是柯里化的，否则它不会等两个 Task 都完成。顺带一提，你要是曾经手动干过这种事，就会由衷感激这个接口简洁得令人震惊。这就是那种让我们离奇点又近一步的漂亮代码。

再看一个例子。

// $ :: String -> IO DOM
const $ = selector => new IO(() => document.querySelector(selector));

// getVal :: String -> IO String
const getVal = compose(map(prop('value')), $);

// signIn :: String -> String -> Bool -> User
const signIn = curry((username, password, rememberMe) => { /* 登录中 */ });

IO.of(signIn).ap(getVal('#email')).ap(getVal('#password')).ap(IO.of(false));
// IO({ id: 3, email: 'gg@allin.com' })

signIn 是个有 3 个参数的柯里化函数，所以我们得相应地 ap。每 ap 一次，signIn 就多收一个参数，直到它凑齐了跑起来。不管需要多少参数，这个模式都能一路续下去。另外要注意：有两个参数是自然而然落在 IO 里的，而最后一个得靠 of 帮一把，把它提进 IO——因为 ap 要求函数和它的所有参数都待在同一个类型里。

兄弟，你举得起来吗？

咱们来看看用无值风格怎么写这些应用函子调用。既然知道 map 等于 of/ap，我们就可以写出通用函数，指定 ap 几次就 ap 几次：

const liftA2 = curry((g, f1, f2) => f1.map(g).ap(f2));

const liftA3 = curry((g, f1, f2, f3) => f1.map(g).ap(f2).ap(f3));

// liftA4，等等

liftA2 这名字挺怪。听着要么像破败工厂里那台难伺候的货梯，要么像廉价加长轿车公司的个性化车牌。不过一旦开了窍，它就一目了然了：把这些零件提升（lift）到应用函子的世界里去。

我头一回看见这堆 2-3-4 的破玩意儿时，只觉得又丑又多余。毕竟在 JavaScript 里我们能查函数的元数（arity），动态地把这东西拼出来。可话又说回来，对 liftA(N) 本身做部分应用往往很有用，所以它的参数长度不能变来变去。

看看实际用法：

// checkEmail :: User -> Either String Email
// checkName :: User -> Either String String

const user = {
  name: 'John Doe',
  email: 'blurp_blurp',
};

//  createUser :: Email -> String -> IO User
const createUser = curry((email, name) => { /* 创建中…… */ });

Either.of(createUser).ap(checkEmail(user)).ap(checkName(user));
// Left('invalid email')

liftA2(createUser, checkEmail(user), checkName(user));
// Left('invalid email')

因为 createUser 收两个参数，我们就用对应的 liftA2。这两条语句是等价的，但 liftA2 那一版压根儿没提 Either。这就让它更通用、更灵活——我们不再跟某个具体类型绑死在一起了。

把前面的例子改用这种写法看看：

liftA2(add, Maybe.of(2), Maybe.of(3));
// Maybe(5)

liftA2(renderPage, Http.get('/destinations'), Http.get('/events'));
// Task('<div>some page with dest and events</div>')

liftA3(signIn, getVal('#email'), getVal('#password'), IO.of(false));
// IO({ id: 3, email: 'gg@allin.com' })

运算符

在 Haskell、Scala、PureScript 和 Swift 这类允许你自定义中缀运算符的语言里，你可能会看到这样的语法：

-- Haskell / PureScript
add <$> Right 2 <*> Right 3

// JavaScript
map(add, Right(2)).ap(Right(3));

知道 <$> 就是 map（又叫 fmap）、<*> 就是 ap，会很有帮助。这能带来更自然的函数应用风格，还能帮忙省掉一些括号。

白送的开罐器

我们还没怎么聊过派生函数。既然这些接口都是层层搭起来的，而且都遵守一套定律，那我们完全可以用更强的接口来定义更弱的接口。

比方说，我们知道应用函子首先得是个函子，所以只要有了应用函子的实例，我们当然就能为自己的类型定义一个函子。

这种完美的计算和谐之所以可能，是因为我们是在一个数学框架里干活。莫扎特就算小时候用 BT 拖下来一个 Ableton，也未必能做得比这更妙。

我前面提过，of/ap 等价于 map。利用这一点，我们可以白捡一个 map：

// 由 of/ap 派生出 map
X.prototype.map = function map(f) {
  return this.constructor.of(f).ap(this);
};

打个比方，单子站在食物链顶端，所以只要有了 chain，函子和应用函子就都是白送的：

// 由 chain 派生出 map
X.prototype.map = function map(f) {
  return this.chain(a => this.constructor.of(f(a)));
};

// 由 chain/map 派生出 ap
X.prototype.ap = function ap(other) {
  return this.chain(f => other.map(f));
};

只要能定义单子，应用函子和函子这两个接口就都能定义出来。这相当了不起——所有这些开罐器都是白拿的。我们甚至可以检视一个类型，把整个过程自动化。

得指出一点：ap 的魅力之一就在于它能并发地跑东西，所以用 chain 来定义它，就等于把这份优化给丢了。尽管如此，在你琢磨最佳实现的同时，先有一个能立刻干活的接口总归是好事。

你可能会问：那干嘛不直接用单子、一了百了？好习惯是：你需要多大的权力就用多大的权力，不多不少。这样能排除掉多余的功能，把认知负担压到最低。所以在应用函子和单子之间，偏爱应用函子是有道理的。

单子有一种独一无二的本事：能把计算排成序列、给变量赋值、还能中止后续执行——全靠它那一路向下的嵌套结构。而看到应用函子的时候，你压根儿不用操这些心。

好，接下来谈谈法律条文……

定律

和我们探索过的其他数学结构一样，应用函子也带着一些有用的性质，供我们在日常代码里依靠。首先你得知道，应用函子是“对组合封闭”的，意思是 ap 绝不会偷偷把容器类型换掉（这又是一个偏爱应用函子而不是单子的理由）。这不是说我们不能有多种不同的效应——我们可以把类型层层叠起来，同时确信在整个应用过程中它们会保持不变。

示范一下：

const tOfM = compose(Task.of, Maybe.of);

liftA2(liftA2(concat), tOfM('Rainy Days and Mondays'), tOfM(' always get me down'));
// Task(Maybe(Rainy Days and Mondays always get me down))

看吧，不用担心有别的类型混进来搅局。

该来看看咱们最爱的范畴论（category theory）定律了：恒等。

恒等

// 恒等
A.of(id).ap(v) === v;

对，也就是说，在函子内部应用 id，不应该改动 v 里的值。比如：

const v = Identity.of('Pillow Pets');
Identity.of(id).ap(v) === v;

Identity.of(id) 这种徒劳无功的写法让我忍不住想笑。不过有趣的是：正如我们已经确认过的，of/ap 跟 map 是一回事，所以这条定律直接就是函子恒等律的推论：map(id) == id。

用这些定律的美妙之处在于：它们就像幼儿园里那个铁腕体育老师，逼着我们所有的接口好好相处、一起玩。

同态

// 同态
A.of(f).ap(A.of(x)) === A.of(f(x));

同态不过就是一个保持结构的映射。事实上，函子就是范畴之间的同态，因为它在映射之下保持了原范畴的结构。

我们其实只是把平常用的函数和值塞进容器里，让计算在容器里面跑，所以无论我们是在容器里把整套东西应用完（等式左边），还是在外面应用完再放进去（右边），结果都一样——这没什么好奇怪的。

快速举个例子：

Either.of(toUpperCase).ap(Either.of('oreos')) === Either.of(toUpperCase('oreos'));

互换

互换律说的是：把函数提升到 ap 的左边还是右边，都无所谓。

// 互换
v.ap(A.of(x)) === A.of(f => f(x)).ap(v);

举个例子：

const v = Task.of(reverse);
const x = 'Sparklehorse';

v.ap(Task.of(x)) === Task.of(f => f(x)).ap(v);

组合

最后是组合律，它无非是用来检验：在容器内部做应用的时候，我们那套标准的函数组合依然成立。

// 组合
A.of(compose).ap(u).ap(v).ap(w) === u.ap(v.ap(w));

const u = IO.of(toUpperCase);
const v = IO.of(concat('& beyond'));
const w = IO.of('blood bath ');

IO.of(compose).ap(u).ap(v).ap(w) === u.ap(v.ap(w));

小结

应用函子的一个好用处，是当你手上有多个函子参数的时候。它们让我们能完全在函子的世界里把函数应用到参数上。虽然用单子也能干这事，但当我们不需要单子那些特有的功能时，就该优先选应用函子。

容器 API 这一块我们快讲完了。我们已经学会了怎么 map、怎么 chain，现在又学会了怎么 ap 函数。下一章我们要学的是：怎么跟多个函子更好地打交道，以及怎么有原则地把它们拆开。

    return f.name ? f.name : f.toString();
  }

  function inspectTerm(t) {
    switch (typeof t) {
      case 'string':
        return `'${t}'`;
      case 'object': {
        const ts = Object.keys(t).map(k => [k, inspect(t[k])]);
        return `{${ts.map(kv => kv.join(': ')).join(', ')}}`;
      }
      default:
        return String(t);
    }
  }

  function inspectArgs(args) {
    return Array.isArray(args) ? `[${args.map(inspect).join(', ')}]` : inspectTerm(args);
  }

  return (typeof x === 'function') ? inspectFn(x) : inspectArgs(x);
}

  }

// NOTE 一个稍微加强版的 `curry`，它还会记录一个函数到底是被部分应用了，
// 还是一次性传齐了所有参数。
// 这有助于在验证练习时给出更有用的提示。
function curry(fn) {
  assert(
    typeof fn === 'function',
    typeMismatch('function -> ?', [getType(fn), '?'].join(' -> '), 'curry'),
  );

  const arity = fn.length;

  return namedAs(fn.name, function $curry(...args) {
    $curry.partially = this && this.partially;

    if (args.length < arity) {
      return namedAs(fn.name, $curry.bind({ partially: true }, ...args));
    }

    return fn.call(this || { partially: false }, ...args);
  });
}


// NOTE 一个稍微加强版的 `compose`，它还会记录被调用函数的链条。
// 最终，用 `compose` 创建出来的函数会带一个 `callees` 变量，
// 里面是所有被调用函数的名字。
// 这有助于在验证练习时给出更有用的提示。
function compose(...fns) {
  const n = fns.length;

  return function $compose(...args) {
    $compose.callees = [];

    let $args = args;

    for (let i = n - 1; i >= 0; i -= 1) {
      const fn = fns[i];

      assert(
        typeof fn === 'function',
        `Invalid Composition: ${ordinal(n - i)} element in a composition isn't a function`,
      );

      $compose.callees.push(fn.name);
      $args = [fn.call(null, ...$args)];
    }

    return $args[0];
  };
}

class Map {
  constructor(x) {
    assert(
      typeof x === 'object' && x !== null,
      'tried to create `Map` with non object-like',
    );

    this.$value = x;
  }

  inspect() {
    return `Map(${inspect(this.$value)})`;
  }

  getType() {
    const sample = this.$value[Object.keys(this.$value)[0]];

    return `(Map String ${sample ? getType(sample) : '?'})`;
  }

  insert(k, v) {
    const singleton = {};
    singleton[k] = v;
    return new Map(Object.assign({}, this.$value, singleton));
  }

  reduce(fn, zero) {
    return this.reduceWithKeys((acc, _, k) => fn(acc, k), zero);
  }

  reduceWithKeys(fn, zero) {
    return Object.keys(this.$value)
      .reduce((acc, k) => fn(acc, this.$value[k], k), zero);
  }

  map(fn) {
    return new Map(this.reduceWithKeys((obj, v, k) => {
      obj[k] = fn(v); // eslint-disable-line no-param-reassign
      return obj;
    }, {}));
  }

  sequence(of) {
    return this.traverse(of, x => x);
  }

  traverse(of, fn) {
    return this.reduceWithKeys(
      (f, a, k) => fn(a).map(b => m => m.insert(k, b)).ap(f),
      of(new Map({})),
    );
  }
}

class Maybe {
  static of(x) {
    return new Maybe(x);
  }

  get isNothing() {
    return this.$value === null || this.$value === undefined;
  }

  get isJust() {
    return !this.isNothing;
  }

  constructor(x) {
    this.$value = x;
  }

  ap(f) {
    return this.isNothing ? this : f.map(this.$value);
  }

  chain(fn) {
    return this.map(fn).join();
  }

  inspect() {
    return this.isNothing ? 'Nothing' : `Just(${inspect(this.$value)})`;
  }

  getType() {
    return `(Maybe ${this.isJust ? getType(this.$value) : '?'})`;
  }

  join() {
    return this.isNothing ? this : this.$value;
  }

  map(fn) {
    return this.isNothing ? this : Maybe.of(fn(this.$value));
  }

  sequence(of) {
    return this.traverse(of, x => x);
  }

  traverse(of, fn) {
    return this.isNothing ? of(this) : fn(this.$value).map(Maybe.of);
  }
}

  }

    return this.chain(x => x);
  }

  map(fn) {
    return new Task((reject, resolve) => this.fork(reject, compose(resolve, fn)));
  }
}

// 还是一次性传齐了所有参数。
// 这有助于在验证练习时给出更有用的提示。
function curry(fn) {
  assert(
    typeof fn === 'function',
    typeMismatch('function -> ?', [getType(fn), '?'].join(' -> '), 'curry'),
  );

  const arity = fn.length;

  return namedAs(fn.name, function $curry(...args) {
    $curry.partially = this && this.partially;

    if (args.length < arity) {
      return namedAs(fn.name, $curry.bind({ partially: true }, ...args));
    }

    return fn.call(this || { partially: false }, ...args);
  });
}


// NOTE 一个稍微加强版的 `compose`，它还会记录被调用函数的链条。
// 最终，用 `compose` 创建出来的函数会带一个 `callees` 变量，
// 里面是所有被调用函数的名字。
// 这有助于在验证练习时给出更有用的提示。
function compose(...fns) {
  const n = fns.length;

  return function $compose(...args) {
    $compose.callees = [];

    let $args = args;

    for (let i = n - 1; i >= 0; i -= 1) {
      const fn = fns[i];

      assert(
        typeof fn === 'function',
        `Invalid Composition: ${ordinal(n - i)} element in a composition isn't a function`,
      );

      $compose.callees.push(fn.name);
      $args = [fn.call(null, ...$args)];
    }

    return $args[0];
  };
}

// 还是一次性传齐了所有参数。

function curry(fn) {
  assert(
    typeof fn === 'function',
    typeMismatch('function -> ?', [getType(fn), '?'].join(' -> '), 'curry'),
  );

  const arity = fn.length;

  return namedAs(fn.name, function $curry(...args) {
    $curry.partially = this && this.partially;

    if (args.length < arity) {
      return namedAs(fn.name, $curry.bind({ partially: true }, ...args));
    }

    return fn.call(this || { partially: false }, ...args);
  });

// 里面是所有被调用函数的名字。
// 这有助于在验证练习时给出更有用的提示。
function compose(...fns) {
  const n = fns.length;

  return function $compose(...args) {
    $compose.callees = [];

    let $args = args;

    for (let i = n - 1; i >= 0; i -= 1) {
      const fn = fns[i];

      assert(
        typeof fn === 'function',
        `Invalid Composition: ${ordinal(n - i)} element in a composition isn't a function`,
      );

      $compose.callees.push(fn.name);
      $args = [fn.call(null, ...$args)];
    }

    return $args[0];
  };

const keepHighest = function keepHighest(x, y) {
  try {
    keepHighest.calledBy = keepHighest.caller;
  } catch (err) {
    // NOTE node.js 运行在严格模式下，禁止使用 '.caller'
    // 这里有个丑陋的 hack，从堆栈跟踪里把调用者捞出来。
    const [, caller] = /at (\S+)/.exec(err.stack.split('\n')[2]);

    keepHighest.calledBy = namedAs(caller, () => {});
  }

  return x >= y ? x : y;
};
